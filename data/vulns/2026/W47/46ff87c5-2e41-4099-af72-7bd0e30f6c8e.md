# In the Linux kernel, the following vulnerability has been resolved\: mm/hugetlb\: fix use\-after\-free of a new anon folio For a fault in a\.\.\.

- **ID**: CVE\-2026\-99506
- **危険度**: High（重要） (CVSS 7.8)
- **OS**: Linux
- **公開**: 2026-11-19

## 原文

In the Linux kernel, the following vulnerability has been resolved\:
  
mm/hugetlb\: fix use\-after\-free of a new anon folio
  
For a fault in a private mapping with nothing in the page cache,  
hugetlb\_no\_page\(\) allocates a folio, locks it and maps it\.  The folio has  
one reference, which belongs to the page table entry from then on\.  After  
dropping the page table lock the function still sets the migratable flag  
of the folio and unlocks it\.
  
Whoever zaps the entry in between frees the folio\.  The fault holds the  
fault mutex and the lock of the vma\.  MADV\_DONTNEED and the first unmap of  
a hole punch, hugetlb\_vmdelete\_list\(\), do not take the fault mutex, and a  
private vma only has a lock if it owns a reservation map\: not with  
MAP\_NORESERVE, and not in the child after fork\(\)\.
  
Then the flag is set in, and folio\_unlock\(\) is called on, a folio that is  
free or has a new owner\.  A surplus page goes back to the page allocator  
while it is locked\:
  
  BUG\: Bad page state in process init  pfn\:108e00  
  flags\: 0x200000000000059\(locked\|uptodate\|dirty\|head\|node\=0\|zone\=2\)  
  page dumped because\: PAGE\_FLAGS\_CHECK\_AT\_FREE flag\(s\) set
  
A page of the pool can be given to the next user, of any file, who locks  
it and loses the lock to the late folio\_unlock\(\)\:
  
  kernel BUG at mm/filemap\.c\:1532\!  
   hugetlb\_no\_page\+0x111b/0x23e0  
   hugetlb\_fault\+0x3a9/0x14a0
  
An unprivileged process is enough\: threads that write to a MAP\_PRIVATE \|  
MAP\_NORESERVE hugetlb mapping, threads that call MADV\_DONTNEED on it, and  
one that takes the freed pages for another file\.
  
Until commit 3a47c54f09c4 \("hugetlbfs\: revert use i\_mmap\_rwsem for more  
pmd sharing synchronization"\) the fault held i\_mmap\_rwsem for reading,  
which everybody who zaps takes for writing\.  The lock that commit  
bf4916922c60 \("hugetlbfs\: extend hugetlb\_vma\_lock to private VMAs"\) gave  
to private vmas closed the window again, but only for those with a  
reservation map\.
  
Be done with the folio before the page table lock is dropped, as  
hugetlb\_wp\(\) is with its copy\.  The function already unlocks page cache  
folios under that lock\.
  
Original fix generated by an LLM and sent in private by Josef\.
