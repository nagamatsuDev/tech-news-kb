# In the Linux kernel, the following vulnerability has been resolved\: fsverity\: Set S\_VERITY only after rollback is no longer possible Co\.\.\.

- **ID**: CVE\-2026\-99476
- **危険度**: High（重要） (CVSS 7.0)
- **OS**: Linux
- **公開**: 2026-11-19

## 原文

In the Linux kernel, the following vulnerability has been resolved\:
  
fsverity\: Set S\_VERITY only after rollback is no longer possible
  
Commit f77f281b6118 \("fsverity\: use a hashtable to find the  
fsverity\_info"\) changed the implementation of FS\_IOC\_ENABLE\_VERITY to  
make concurrent reads start going through fsverity verification slightly  
earlier than they did before\.
  
Instead of it happening when enable\_verity\(\) calls fsverity\_set\_info\(\),  
it now happens when \-&gt;end\_enable\_verity\(\) sets S\_VERITY\.
  
However, ext4 and btrfs can roll back verity after they set S\_VERITY,  
causing a use\-after\-free\.
  
Fix that by making ext4 and btrfs set S\_VERITY only after rollback is no  
longer possible\.  On failure, don't roll back S\_VERITY, but do roll back  
the filesystem\-specific verity flag\.
  
Also update enable\_verity\(\) to handle any future instances of this bug  
more safely by warning and \*not\* freeing the fsverity\_info\.
  
Finally, tweak some comments\.  Clarify one, and move information from  
another to its proper place in the comment for \-&gt;end\_enable\_verity\(\)\.
