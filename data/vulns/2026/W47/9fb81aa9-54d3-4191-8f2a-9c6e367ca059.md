# In the Linux kernel, the following vulnerability has been resolved\: drm/amdgpu/gfx12\: disallow GFXOFF while updating the SPM VMID gfx\_v\.\.\.

- **ID**: CVE\-2026\-99627
- **危険度**: High（重要） (CVSS 7.1)
- **OS**: Linux
- **公開**: 2026-11-20

## 原文

In the Linux kernel, the following vulnerability has been resolved\:
  
drm/amdgpu/gfx12\: disallow GFXOFF while updating the SPM VMID
  
gfx\_v12\_0\_update\_spm\_vmid\(\) does a read\-modify\-write of RLC\_SPM\_MC\_CNTL  
over MMIO without keeping GFX powered, unlike gfx11\. When GFX is in  
GFXOFF at that point the update doesn't stick, and with the SPM VMID  
programmed on submission again, the job of a process with a reserved  
VMID can still run with the SPM writing through VMID 0\.
  
On navi48, after a few other submissions and a VM fault on the same VM,  
a COPY\_DATA of RLC\_SPM\_MC\_CNTL from such a job reads 0 although the  
update was called for it\:
  
  \$ amd\_uapi\_regression \-\-run\-subtest cs\-secure\-ib\-compute,gem\-mapping\-info\-high\-va,gpuvm\-fault\-high\-va,reserved\-vmid\-spm\-vmid  
  amdgpu 0000\:03\:00\.0\: \[gfxhub\] page fault \(src\_id\:0 ring\:40 vmid\:7 pasid\:185\)  
  amdgpu 0000\:03\:00\.0\: 	 Faulty UTCL2 client ID\: SDMA1 \(0xe\)  
  RLC\_SPM\_MC\_CNTL in the job\: 0x00000000
  
With GFXOFF disallowed around the update it reads the reserved VMID 15\.
  
\(cherry picked from commit 907aebc5578ae09fa5c0e2f0784201295837e60b\)
