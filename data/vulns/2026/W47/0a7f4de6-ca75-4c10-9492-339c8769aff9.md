# In the Linux kernel, the following vulnerability has been resolved\: rtnetlink\: wait for RCU readers in rtnl\_link\_unregister\(\) rtnl\_link\.\.\.

- **ID**: CVE\-2026\-99401
- **危険度**: High（重要） (CVSS 7.0)
- **OS**: Linux
- **公開**: 2026-11-19

## 原文

In the Linux kernel, the following vulnerability has been resolved\:
  
rtnetlink\: wait for RCU readers in rtnl\_link\_unregister\(\)
  
rtnl\_link\_ops\_get\(\) finds ops on link\_ops under rcu\_read\_lock\(\) and only  
then takes ops\-&gt;srcu\. rtnl\_link\_unregister\(\) unlinks ops, then calls  
synchronize\_srcu\(\) and cleanup\_srcu\_struct\(\) without first waiting for  
RCU readers\. A reader that found ops before list\_del\_rcu\(\) and has not yet  
taken ops\-&gt;srcu is not waited for\.
  
Such a reader then locks a cleaned\-up srcu\_struct and keeps using ops  
after the module that owns it is gone\. rtnl\_newlink\(\) and  
rtnl\_dump\_ifinfo\(\) both look up ops without RTNL, the latter for any  
user that dumps links filtered by kind\.
  
With delays added between the lookup and srcu\_read\_lock\(\) in  
rtnl\_link\_ops\_get\(\), and before rtnl\_link\_ops\_put\(\) in  
rtnl\_dump\_ifinfo\(\), running "ip link show type dummy" alongside  
"rmmod dummy" on a KASAN kernel gives\:
  
  BUG\: KASAN\: vmalloc\-out\-of\-bounds in \_\_srcu\_read\_unlock\+0x57/0x70  
  Read of size 8 at addr ffffffffc02ff318 by task ip/147  
  Call Trace\:  
   \_\_srcu\_read\_unlock\+0x57/0x70  
   rtnl\_dump\_ifinfo\.cold\+0x30/0x3b  
   rtnl\_dumpit\+0x7a/0x1b0  
   netlink\_dump\+0x486/0x11b0  
   \_\_netlink\_dump\_start\+0x661/0x910  
   rtnetlink\_rcv\_msg\+0x611/0x9e0  
   netlink\_rcv\_skb\+0x126/0x380  
   netlink\_unicast\+0x605/0x830  
   netlink\_sendmsg\+0x6d0/0xbb0  
   \_\_sys\_sendto\+0x335/0x3a0
  
Call synchronize\_rcu\(\) before synchronize\_srcu\(\), as  
rtnl\_af\_unregister\(\) already does\. This should be enough because  
rtnl\_link\_ops\_get\(\) is the only RCU walker of link\_ops, and it takes  
ops\-&gt;srcu before rcu\_read\_unlock\(\), so every reader that found ops is  
covered by synchronize\_srcu\(\) once the RCU grace period ends\. The extra  
grace period only costs time at module unload\.
  
Readers and the writer were serialized by RTNL until link\_ops got its  
own mutex, which is why the missing RCU wait did not matter before\.
