# In the Linux kernel, the following vulnerability has been resolved\: mm/userfaultfd\: only allocate anon\_vma in CoW mappings find\_vma\_and\.\.\.

- **ID**: CVE\-2026\-99580
- **危険度**: High（重要） (CVSS 7.8)
- **OS**: Linux
- **公開**: 2026-11-20

## 原文

In the Linux kernel, the following vulnerability has been resolved\:
  
mm/userfaultfd\: only allocate anon\_vma in CoW mappings
  
find\_vma\_and\_prepare\_anon\(\) can end up allocating an anon\_vma in VMAs that  
are not CoW mappings, which is wrong\.
  
If we have a MAP\_SHARED R/O file mapped, we lack VM\_SHARED \(but do have  
VM\_MAYSHARE\) and lack VM\_MAYWRITE\.
  
While uffd later rejects such mappings \(uffd registration requires  
VM\_MAYWRITE, see comment in validate\_dst\_vma\) find\_vma\_and\_prepare\_anon\(\)  
still wrongly allocates an anon vma before it validates the vma\.
  
This in turn later confuses copy\_page\_range\(\)\-&gt;vma\_needs\_copy\(\) such  
that we end up calling copy\_hugetlb\_page\_range\(\) with ranges that  
actually do not contain \*any\* per\-pagetable information that would  
require copying, which is the basis for PMD\-table sharing in the first  
place\.
  
copy\_hugetlb\_page\_range\(\) should not have to worry about shared  
PMD tables at all\: it doesn't make any sense to copy page tables that are  
shared, as they can be fully recreated later\. Ending up in the function  
with shareable page tables is the real issue\.
  
If a destination PMD table is shared in copy\_hugetlb\_page\_range\(\), it  
might get concurrently unshared as we are not holding relevant  
locks, resulting in us using a page table that is no longer mapped and  
possibly freed after calling\:
  
	dst\_pte \= huge\_pte\_alloc\(dst, dst\_vma, addr, sz\);
  
To fix it, do not allocate an anon\_vma in non\-CoW mappings and add a  
safety guard to copy\_hugetlb\_page\_range\(\), making sure that we never  
end up messing with shared PMD tables in there\.
  
Before commit 867a43a34ff8a \("userfaultfd\: use per\-vma locks in userfaultfd  
operations"\) we would always validate the VMA before allocating an  
anon\_vma, and consequently never wrongly allocate an anon\_vma\.
  
As uffd\_lock\_vma\(\) is part of the same lookup machinery and  
also contains a misleading VM\_SHARED check, change that one as well  
directly for consistency\.
  
A follow\-up cleanup will stop taking the hugetlb\_vma\_lock\_read\(src\_vma\)  
lock in copy\_hugetlb\_page\_range\(\) entirely\. Further, the usage of  
VM\_SHARED in userfaultfd code should be cleaned up later to focus on  
CoW vs\. non\-CoW mappings\.
