# In the Linux kernel, the following vulnerability has been resolved\: mm/ksm\: fix use of a freed anon\_vma at swap\-in A folio read from a \.\.\.

- **ID**: CVE\-2026\-99650
- **危険度**: High（重要） (CVSS 7.8)
- **OS**: Linux
- **公開**: 2026-11-20

## 原文

In the Linux kernel, the following vulnerability has been resolved\:
  
mm/ksm\: fix use of a freed anon\_vma at swap\-in
  
A folio read from a swap slot previously shared by KSM can remain in the  
swap cache after the process that first mapped it exits\. Its anon\_vma  
can then be freed, so ksm\_might\_need\_to\_copy\(\) must not dereference it  
to compare roots\.
  
Doing so can result in some false\-positives, resulting in the reverse  
mapping missing the new folio mapping, preventing migration and reclaim\.
  
SLAB\_TYPESAFE\_BY\_RCU allows individual anon\_vma objects to be reused  
immediately after freeing\. A stale pointer can then refer to another  
anon\_vma whose root matches, even though the target VMA is not linked  
to that anon\_vma\.
  
Move the anonymous rmap compatibility checks into  
folio\_anon\_rmap\_compatible\(\)\. Keep the page\-index check and compare the  
folio's anon\_vma pointer against the VMA's own anon\_vma and root first\.
  
If neither matches, bite the bullet and walk the VMA's anon\_vma\_chain\.  
The VMA keeps these anon\_vmas alive, and finding a match guarantees that  
reverse mapping can find the new mapping\.
  
Lorenzo Stoakes says in a private discussion\:
  
  "This isn't quite equivalent to the existing check\.
  
  Every anon\_vma in an anon\_vma\_chain shares the same root, but if you  
  split a VMA then fork both of them like this\:
  
                  VMA A  
               /        \\         &lt;split&gt;  
            VMA B      VMA C  
               \\        /  
        root &lt;\- anon\_vma 1  
               \-\-\-\-\^ \^\-\-\-\-        &lt;fork&gt;  
              /   parent  \\  
        anon\_vma 2   anon\_vma 3  
             \|            \|  
           VMA D        VMA E
  
  VMA's D and E both get their own new  
  anon\_vma's such that\:
  
  VMA D\: anon\_vma 2 \-&gt; anon\_vma 1 \-&gt; root  
  VMA E\: anon\_vma 3 \-&gt; anon\_vma 1 \-&gt; root
  
  And if you found a folio referencing anon\_vma 2, the existing check\:
  
	anon\_vma\-&gt;root \=\= vma\-&gt;anon\-vma\-&gt;root
  
  Would be true for VMA's B, C, D &amp; E\.
  
  However after your change it'd be true for VMA D only, as it's the only  
  one with anon\_vma 2 in its anon\_vma\_chain\.
  
  Whether or not that could actually happen in practice\.\.\. 🙂 I don't  
  know\.
  
  \[\.\.\.\] after your change it'd be true for VMA D only, as it's the only  
  one with anon\_vma 2 in its anon\_vma\_chain\. \[\.\.\.\] I would \[\.\.\.\] say that  
  you are making the test stricter but more correct\.  
"
  
If this affects performance when KSM was never even involved, we could  
just track whether KSM ever merged anything and just skip these checks\.
  
There isn't really a lot we can do otherwise\: for mapped folios we might  
be able to use folio\_get\_anon\_vma\(\), but for unmapped folios there really  
is no easy way to see if the anon\_vma is still valid\.
  
Document the \(confusing\) lifetime requirements of folio\_anon\_vma\(\)\.
