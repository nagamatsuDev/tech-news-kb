# In the Linux kernel, the following vulnerability has been resolved\: mm/rmap\: don't discard lazyfree THPs at PMD level \_\_discard\_anon\_fo\.\.\.

- **ID**: CVE\-2026\-99463
- **危険度**: High（重要） (CVSS 7.8)
- **OS**: Linux
- **公開**: 2026-11-19

## 原文

In the Linux kernel, the following vulnerability has been resolved\:
  
mm/rmap\: don't discard lazyfree THPs at PMD level
  
\_\_discard\_anon\_folio\_pmd\_locked\(\) clears a lazyfree THP's PMD before it  
determines whether the folio can be discarded, and restores it if the  
folio is dirty or has extra references\.  It is done under only the PMD  
lock and the anon\_vma read lock inside try\_to\_unmap\_one\(\) and no mmap lock  
is held\.  The temporarily none PMD causes UAF\.
  
A parallel munmap\(\) or mremap\(\) is supposed to serialize with it on the  
PMD lock, but zap\_pmd\_range\(\) \(called by munmap\(\)\) and move\_page\_tables\(\)  
\(called by mremap\(\)\) do not take the lock when they see the temporarily  
none PMD and skip the PMD\.  There is no more page table walk after the  
none PMD is restored\:
  
\- munmap\(\)\: free\_pgtables\(\) waits in unlink\_anon\_vmas\(\) for the anon\_vma  
  lock, then free\_pmd\_range\(\) drops the restored PMD as bad without  
  removing the rmap, so the folio keeps a stale mapcount\.
  
\- whole\-VMA MREMAP\_DONTUNMAP\: dontunmap\_complete\(\) unlinks the source VMA  
  from its anon\_vma while the restored PMD still maps the folio\.
  
\- plain mremap\(\)\: the THP is not moved but unmapped, so the THP's data is  
  lost\.
  
In the first two cases, the folio stays mapped, but no VMA that maps it is  
linked to its anon\_vma\.  When the anon\_vma is freed, it is still reachable  
when one rmap walks the folio\.  Racing lazyfree reclaim against  
MREMAP\_DONTUNMAP as an unprivileged user reproduces a KASAN use\-after\-free  
in folio\_lock\_anon\_vma\_read\(\) as reported in the Closes link\.
  
One solution is to use an invalidated PMD instead of a cleared one until  
the discard is committed, but it needs arch fixes first\.  
1\. GUP\-fast still follows an invalidated PMD on riscv, LoongArch and s390\.  
2\. sparc64 miscounts thp\_pte\_count when an invalidated PMD is set again or  
   cleared\.
  
To keep the fix simple for backport, stop discarding lazyfree THPs at PMD  
level instead\. try\_to\_unmap\_one\(\) splits the PMD and discards the folio at  
PTE level\.
  
unmap\_huge\_pmd\_locked\(\) and \_\_discard\_anon\_folio\_pmd\_locked\(\) are left in  
place, unused, to minimize this fix for backport and the invalidated PMD  
approach is planned as a follow\-up series to use them again\.
