# z\_impl\_pwm\_capture\_cycles\(\) in drivers/pwm/pwm\_capture\.c stores its capture context \(struct z\_pwm\_capture\_cb\_data, including a struct k\_s\.\.\.

- **ID**: CVE\-2026\-102957
- **危険度**: High（重要） (CVSS 7.7)
- **公開**: 2026-11-25

## 原文

z\_impl\_pwm\_capture\_cycles\(\) in drivers/pwm/pwm\_capture\.c stores its capture context \(struct z\_pwm\_capture\_cb\_data, including a struct k\_sem\) on its own stack and registers a pointer to it as the driver capture callback's user\_data\. When called with a K\_NO\_WAIT timeout, k\_sem\_take\(\) returns \-EBUSY, which the function did not handle\: it fell through, returned the uninitialized status field, copied uninitialized period/pulse values to the caller when that status happened to be zero, and returned without disabling the capture or clearing the callback\.
  
pwm\_capture\_cycles\(\) is a system call, and z\_vrfy\_pwm\_capture\_cycles\(\) passes the caller's timeout through unchanged\. With CONFIG\_USERSPACE and CONFIG\_PWM\_CAPTURE enabled, an unprivileged user\-mode thread that has been granted access to a capture\-capable PWM device can pass K\_NO\_WAIT to trigger the defect\. Without userspace the function is only reachable from trusted application code\.
  
The uninitialized values come from the thread's privileged \(kernel\) stack, so a user\-mode caller can read up to 8 bytes of stale kernel stack memory per call\. More seriously, when the capture later completes, the driver ISR invokes z\_pwm\_capture\_cycles\_callback\(\) with the dangling pointer\. The callback writes into the expired kernel stack region and calls k\_sem\_give\(\) on whatever memory now occupies it, which can corrupt live kernel stack frames and make the scheduler walk a forged wait queue\. The result is kernel memory corruption from interrupt context, leading at least to a crash and possibly to privilege escalation out of the userspace sandbox\. The fix rejects K\_NO\_WAIT with \-EINVAL before any capture is configured\.
