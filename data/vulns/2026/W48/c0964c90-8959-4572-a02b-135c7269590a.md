# The system call verification handlers for smbus\_block\_read\(\) and smbus\_block\_pcall\(\) in drivers/smbus/smbus\_handlers\.c \(z\_vrfy\_smbus\_bloc\.\.\.

- **ID**: CVE\-2026\-100374
- **危険度**: High（重要） (CVSS 7.8)
- **公開**: 2026-11-23

## 原文

The system call verification handlers for smbus\_block\_read\(\) and smbus\_block\_pcall\(\) in drivers/smbus/smbus\_handlers\.c \(z\_vrfy\_smbus\_block\_read\(\) and z\_vrfy\_smbus\_block\_pcall\(\)\) validated the device object, the count pointers and \(for process call\) the send buffer, but never validated the receive buffer \(buf / rcv\_buf\)\. The call then proceeds into the driver implementation, which runs in supervisor mode and writes the bytes received from the SMBus peripheral through that pointer\.
  
A user\-mode thread on a system built with CONFIG\_USERSPACE that has been granted access to an SMBus device object can pass an arbitrary address, including kernel data or another thread's memory, as the receive buffer\. The driver then writes up to SMBUS\_BLOCK\_BYTES\_MAX \(32\) bytes of peripheral\-supplied data there \(the STM32 driver writes as many bytes as the peripheral's length byte announces, up to 255\)\. The address is fully attacker\-chosen; the written content comes from the bus and is typically influenceable by the caller through the choice of peripheral and command, or by first writing data to a device that echoes it back\.
  
This breaks the user/kernel isolation boundary\: it gives an unprivileged thread a kernel\-memory write primitive usable for privilege escalation, or at minimum to corrupt kernel state or crash the system\. The fix adds K\_SYSCALL\_MEMORY\_WRITE\(\) checks of the receive buffer for the documented worst case, SMBUS\_BLOCK\_BYTES\_MAX\. Systems without CONFIG\_USERSPACE are not affected\.
