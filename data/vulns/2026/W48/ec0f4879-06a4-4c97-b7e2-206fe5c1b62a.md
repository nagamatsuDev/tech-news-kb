# With SQL\_C\_DEFAULT, the C type of a bound column or parameter follows its SQL type\.

- **ID**: CVE\-2026\-136512
- **危険度**: High（重要） (CVSS 7.5)
- **公開**: 2026-11-25

## 原文

With SQL\_C\_DEFAULT, the C type of a bound column or parameter follows its SQL type\. An application sizes its buffer from the type it was told when it described the statement\. When the column had another type at fetch time, because the server reported another type, the table was altered, or an output parameter's result column had another type, psqlODBC wrote the larger type into the smaller buffer\: 12 bytes past a 4\-byte buffer for a uuid, and more in multi\-row fetches, where the driver also steps through the array by the larger size\.
  
Other conversions wrote past the application's buffer as well\:
  
\- With Int8As set to a smaller type, an int8 column fetched as SQL\_C\_DEFAULT was still written as 8 bytes\.  
\- An int2vector column fetched as SQL\_C\_DEFAULT returned unterminated binary data instead of text\.  
\- An output parameter that the application discards by binding a NULL buffer overflowed a stack buffer in the driver\.  
\- SQLGetData\(\) with BufferLength 0 on a column the driver reads as a large object wrote a NUL byte past the buffer\.  
\- Adding a row with SQLBulkOperations\(SQL\_ADD\) on a static updatable cursor before the first fetch, then changing that row, rolling back and fetching it, made the keyset index arithmetic free a pointer that was never allocated and corrupt the heap\.
  
This can be triggered by a hostile or compromised server, or anyone on the network path of a connection that does not use sslmode\=verify\-full \(the default is disable\), and by the owner of a table the application reads\.
  
Versions up to and including psqlODBC 18\.00\.0006 are affected\.
